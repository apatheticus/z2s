## What this is

Most projects write a specification, then build something else. The document ages
in a folder while the code drifts away from it, and nobody can say which one is
true any more.

Zero-to-Ship closes that gap by making the specification the input rather than the
preamble. Seven documents are written in order, each one refusing to start until
the document above it exists. The plan is derived from those documents, so every
requirement traces to a unit of work and any requirement nothing claims fails the
build. When the work runs, each unit is
briefed from the plan, checked by a verification gauntlet, and graded by a second
process that never sees the builder's own report.

The method is written in its own notation and generated by its own toolchain. The
specification set published at
[apatheticus.github.io/z2s](https://apatheticus.github.io/z2s/) was produced this
way and passes its own gates, which is the only evidence here worth much.

## Who it's for

Someone who has to hand work to an agent, or to a team, and needs the handover to
carry the whole brief. It suits a project where scope is argued once and settled
in writing. It fits badly where requirements arrive verbally and change weekly.

## How the chain works

Seven documents, written in order. Each generator refuses to run without the
documents it reads from, so the order is enforced rather than suggested.

| Step | Writes | Refuses without |
| --- | --- | --- |
| `/zero:vision` | Vision, with a register of every source | — |
| `/zero:context` | Glossary, bounded contexts, context map | Vision |
| `/zero:prd` | Product requirements, goals, journeys, measures | Context, Vision |
| `/zero:fsd` | Functional specification (`FR-…`) | PRD, Context |
| `/zero:stories` | User stories, use cases, acceptance criteria | FSD, Context |
| `/zero:sdd` | Technical design, decisions (`ADR-…`), targets | FSD, Context |
| `/zero:plan` | Milestones, phases, tasks, criteria, coverage proof | FSD, SDD, Stories, Context |

Seven more skills operate on the set instead of extending it: `/zero:init` sets a
project up, `/zero:action` resumes from wherever the set stands, `/zero:build`
works the plan wave by wave, `/zero:prompt` prints the instructions for one unit,
`/zero:update` folds changes in forward-only, `/zero:ship` commits and pushes, and
`/zero:questions` is the clarification interview every other skill routes through.

Three rules hold across all of them.

- **Identifiers are permanent.** A document grows by addendum. Nothing is
  renumbered and nothing is deleted; a withdrawn requirement is retired and keeps
  its number.
- **A gap becomes a question, never a guess.** Where a generator cannot ground an
  entry in something upstream, it records an open question and leaves the entry
  out.
- **Coverage cannot be turned off.** A requirement no task claims fails the run,
  and no configuration setting lowers that bar.

## How the work runs

Every unit of work goes round the same loop, and that loop is what keeps a claim of
"done" honest.

Three things in that picture were decided deliberately, and each could reasonably have
gone the other way.

- **The gauntlet is run by the orchestrator, not by the worker.** The exit status is
  observed, so a unit cannot pass by reporting that it did.
- **The judge is a different process, and its brief never carries the builder's
  report.** It is shown the work and the evidence, never the account of how the work
  was made.
- **A retry is briefed with the one gap the last judgement named**, and a fresh judge
  sees it — otherwise a judge grades improvement instead of the bar. Attempts are
  bounded, because one impossible unit must not idle a whole run.

## Technology stack

| Area | Choice |
| --- | --- |
| Language | Python 3 |
| Runtime dependencies | None. Standard library only |
| Documents | Self-contained HTML with an embedded machine-readable specification |
| Document runtime | Browser built-ins, inlined into each file |
| Distribution | A Claude Code plugin, `zero` |
| Tests | `unittest`, with browser tests through Playwright when it is installed |

The zero-dependency rule is a requirement of the method (`NFR-ARC-03`), not a
preference. It is what lets a generated document open anywhere with no server, no
build step, and no network.

## Project structure

```
z2s/            the toolchain: one module per generator, plus the shared chain,
                validator, trace engine, planner, orchestrator and gates
skills/         15 SKILL.md files, one per step, shipped as the `zero` plugin
selfhost/       the method's own briefs, and the build that regenerates .zero/
.zero/          the method described in its own notation, generated by itself
docs/           the published specification set and the GitHub Pages source
docs/_build/    the specs and generator behind those published documents
reference/      the chain rules a skill points an operator at
tests/          the test suite, including real-browser checks
```

## Getting started

### Prerequisites

- Python 3, from the system or any recent install. Nothing else is required to
  generate or check documents.
- [Claude Code](https://claude.com/claude-code), to drive the method through its
  skills.
- Playwright, optional. Without it the browser tests skip rather than fail.

### Install the plugin

```
/plugin marketplace add apatheticus/z2s
/plugin install zero@z2s
```

Then, in the project you want to specify:

```
/zero:init
/zero:vision
```

`/zero:action` will work out where the chain stopped and carry on from there, so
it is the only command you need to remember afterwards.

### Or drive the toolchain directly

The skills are a door onto the modules, and the modules run on their own:

```bash
python3 -m z2s.project                    # set the project up
python3 -m z2s.author run vision          # write the next document, or print the next question
python3 -m z2s.pipeline .zero/specs/*.html .zero/plan/*.html   # every gate, in one run
python3 -m z2s.trace .zero/specs/*.html .zero/plan/*.html      # what exists, who owns it, who claimed it
python3 -m z2s.execute run                # work the plan
```

`z2s.author run` exits `3` when it has a question for you and `0` once the
document is written, so it drives cleanly from a script.

### Regenerate the published set

```bash
cd docs/_build
python3 generate.py     # rebuild the published documents and run the coverage gate
python3 check.py        # validate the rendered HTML and prove the build is deterministic
```

Never edit a generated `.html` by hand. Edit the spec and regenerate.

## Testing

```bash
python3 -m unittest discover -s tests
```

Browser tests launch real Chromium through Playwright and skip when it is absent.
They are the only tests that need anything outside the standard library.
